# ADR 0003 — Finding ids are a short per-job sequence, not a UUID

- **Status:** Accepted
- **Date:** 2026-08-14
- **Affects:** `agents/researcher.py` · `docs/ARCHITECTURE.md` §5.2, §9 ·
  `docs/engineering-guidelines.md` §2.3, §9
- **Found by:** The 6-job diagnostic run of 2026-08-13 — `measure-04` failed
  `report_cites_unknown_findings`

---

## Context

`finding_id` is the audit link. A `Claim` carries the `finding_ids` it came from, `Report.sources` is
derived from those ids, and the export gate refuses any claim that cannot reach a source URL through
them (invariant 1). Every one of those relationships is built from a string the **model** wrote.

It is the only identifier in the system the model is asked to copy. Two others are deliberately not:

- The Planner numbers subtopics `s1`, `s2`, `s3` — short by design, and the prompt asks for exactly
  that.
- `claim_id` is minted in `agents/synthesizer.py` **after** the model answers, replacing whatever the
  model produced, precisely so that a claim's identity never depends on transcription.

`finding_id` was `uuid4().hex` — 32 opaque hexadecimal characters. The Synthesizer prompt lists one
block per finding, each headed `finding_id: <32 chars>`, and the model must reproduce those strings
exactly in `Claim.finding_ids`.

### What the failure looked like

`measure-04` ("Compare Zoom and Microsoft Teams on enterprise video conferencing") ran 45 findings
into the Synthesizer and failed on the guard at `agents/synthesizer.py`:

```text
agents.synthesizer report cites findings that do not exist: ['087accf6f9a94fb38418d17b58883fb']
```

That id is **31 characters**. `uuid4().hex` is always 32. The model did not invent an identifier — it
dropped a single character while transcribing one of 45 opaque strings.

The job spent **592 seconds and 26 LLM calls** and produced nothing: no report, no claims, no
sources.

### Why the guard is not the problem

The guard behaved correctly and is not being relaxed. A claim citing a finding that does not exist
has no audit trail, and gl §3 is explicit that a wrong value which survives into the report looks
deliberate. Failing the job is the right response to a broken audit link.

The problem is upstream: the system chose an identifier format that makes the transcription hard, for
no benefit it was collecting. Nothing needed `finding_id` to be a UUID. It is generated by us, read
by us, and never joined across jobs — §9's own note already says "a finding belongs to exactly one
job — evidence is never shared between jobs".

### Why this was not visible before

The n=20 baseline of 2026-08-13 had four failures and **all four were `llm_call_failed`** — transport
problems, not content problems. This failure mode had never been observed. It is a probabilistic
transcription error, so it appears as a function of how many ids a job asks the model to copy, which
is why the job with 45 findings is where it surfaced.

---

## Decision

**Findings are numbered `f1`, `f2`, … as a per-job sequence, assigned in code after the extraction
pool has joined.**

Two parts, and the second is the load-bearing one.

**The format.** `f` plus a decimal counter. Short enough to copy without error, and consistent with
`s1`–`s5` for subtopics, so the two identifier vocabularies in a prompt now look alike.

**Where it is assigned.** In `_extract`, in the loop that collects results in page order — *not* in
`_findings_from`, which is where `uuid4().hex` used to be called.

That placement is forced by [ADR 0002](0002-concurrent-page-extraction-in-the-researcher.md).
`_findings_from` runs on a pool of up to `RESEARCHER_CONCURRENCY` threads. Two workers numbering from
a shared counter is a race, and the prize for losing it is two findings answering to one id — which
would not raise anything, would not fail the export gate, and would silently carry a claim to the
wrong source. `_extract` collects after the pool has joined, so numbering there is single-threaded
and follows page order, like the findings themselves.

**The sequence is per job, not per Researcher visit.** Findings accumulate across visits through the
`operator.add` reducer on `ResearchState`, so `_extract` is told where to start:
`first_number=len(state["findings"]) + 1`. A visit that restarted at `f1` would mint an id a
different finding already holds.

### Verified

Three tests, each confirmed to fail against the previous code — the id format, continuation across
Researcher visits, and that concurrent extractions cannot share an id.

`measure-04` was then re-run against the real endpoint and the real web. It reached `approved` in
895s / 31 calls. The trace shows the model was offered `f1`…`f83`, every one matching `^f\d+$`, and
citing **73 distinct ids with none unknown to the findings** — 73 claims, 12 sources, 73 supported, 0
unsupported.

That is n=1 against a probabilistic failure. It demonstrates the mechanism works end to end; it does
not quantify the rate the change prevents, and no such rate is claimed.

## Alternatives considered

**Keep the UUID and repair the citation instead** — fuzzy-match an unknown id to the nearest known
one. Rejected: a nearest match on an opaque hex string is a guess about which source a claim came
from, and the audit trail is the one thing in this system that may not be guessed. It also makes the
guard unable to distinguish a typo from a fabrication.

**Keep the UUID and drop the offending claim** rather than failing the job. Rejected for now: it
converts a loud failure into a quiet content loss, and the claim that gets dropped is not necessarily
the wrong one. Worth revisiting only if short ids still produce misses.

**Number them but keep the ids globally unique** — `{job_id}-f1`. Rejected: it restores most of the
length that caused the problem, to buy a global uniqueness nothing reads. §9 already scopes findings
to a job.

**Have the model cite by array index** instead of an id. Rejected: index citation breaks the moment
the findings list is filtered or reordered between passes, and reflection's Researcher route does
exactly that.

---

## Consequences

### What gets better

- The transcription failure class is removed at its source, rather than detected after 592 seconds.
- The Synthesizer prompt loses roughly 29 characters per finding of pure identifier — at 83 findings,
  about 2.4k characters. Small, and free.
- A trace is readable by a human. `f7` in a claim can be found in the prompt by eye; a 32-character
  hex string cannot.

### What we accept

- **`finding_id` is unique within a job, not globally.** This is the real cost and it lands on
  Phase 2. `ARCHITECTURE.md` §9 declared `findings (finding_id PK, …)`, which is no longer true —
  every job now has an `f1`. The schema in §9 has been corrected to a composite
  `PRIMARY KEY (job_id, finding_id)`, with `claim_sources` carrying `job_id` so its foreign key still
  resolves. No migration exists yet, so this is a correction to a plan rather than a change to a
  database.
- The id is not meaningful outside its job. Anything that ever needs to name a finding globally must
  carry `job_id` with it — a log line, an eval record, a support question.
- Identity is now assigned in a different place from where the `Finding` is constructed.
  `_findings_from` builds a `Finding` with an empty `finding_id`, which is only safe because
  `_extract` is its sole caller and numbers everything it collects. A second caller would have to
  number too, and nothing enforces that.

### Unchanged

- The guard in `agents/synthesizer.py` and invariant 1. A claim citing an unknown finding still fails
  the job.
- `claim_id` still being minted in code after the model answers, for its own separate reason
  (`ARCHITECTURE.md` §5.3).
- Everything about provenance. `url`, `title`, `retrieved_at`, `content_hash` and `truncated` still
  come from the tool result and never from the model.
- Findings still come back in page order (ADR 0002), which is what makes the numbering deterministic
  across two runs over the same sources.

### Revisit when

- A job ever needs more findings than a reader can hold — `f1`…`f400` is still short, but the
  Synthesizer prompt has other limits first.
- Phase 2's migration is written, at which point the composite key stops being a documented intention
  and becomes a constraint.
- A `report_cites_unknown_findings` failure recurs with short ids, which would mean the length was
  not the mechanism and the alternatives above deserve another look.
